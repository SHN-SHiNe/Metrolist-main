# 多音频库设计

## 目标

SHiNe MUSIC 把一个可独立连接、扫描和保护的音乐根目录称为“音频库”。一个实例可同时管理 NAS 本地目录、USB 硬盘、网络挂载和云盘挂载。

## 边界和不变量

- 新增音频库必须是 `SHINE_LIBRARY_DIR` 的子目录；容器默认为 `/libraries`。
- 每个容器内路径只能注册一次，不允许父子库重叠；真实路径不得通过符号链接逃出 `/libraries`。注册后路径不可修改。
- 只有已启用、可写且当前在线的库才能成为下载目标，全局最多一个下载目标。
- 只读库可扫描和播放，但不能通过 SHiNe 删除曲目。
- 停用音频库会停止扫描并保留已有索引。
- 路径不存在、不可读或扫描结果意外为空时，库进入 `offline` 状态，保留原曲目索引。若用户确实主动清空了目录，可在页面二次确认后执行 `allowEmpty` 扫描来清除旧索引。
- 重新连接设备并成功扫描后，该库恢复 `online`，增量更新它自己的曲目。

## 数据和接口

`tracks.library_id` 将曲目归属到 `music_libraries`。每次扫描会话只能标记所属库的曲目，不会影响其他设备。

- `GET /api/libraries`：列出库、连接状态、曲目数和扫描错误。
- `POST /api/libraries`：注册音频库。
- `PUT /api/libraries/{id}`：改名、启停、设备类型、只读和下载目标配置。
- `POST /api/libraries/{id}/scan`：单独扫描一个库；仅在用户确认目录已主动清空时传入 `allowEmpty=true`。
- `GET /api/library?libraryId={id}`：在服务端筛选某个库，再执行搜索、排序和分页。

## 运维约定

宿主机先将每个设备挂载到稳定路径，Compose 再将它们映射到 `/libraries/<id>`。SHiNe 不负责挂载 SMB/NFS/云盘，只观察容器内路径是否可用。这使挂载凭据不需要进入 SHiNe 数据库。
